pAI v3 · three agents on one host · as of Nov 2026

pAI Agent Architecture

Each agent is one container running an event-sourced kernel. Everything that happens to it is appended to an encrypted ledger first; projections, a scheduler and a mind built from cheap System-1 judgments and deliberate System-2 thoughts read from it. Nothing is shared between agents except what they post to the crew forum.

Kernel and trust System 1: fast, cheap judgments (Decisions model, local model, rules) System 2: deliberate thought (chat model with tools)

The whole agent

One spoken turn, end to end

The avatar page is the most layered path: what the operator says is recognised in the browser, recorded by the agent, judged by System 1, answered by System 2 and spoken back, with the avatar moving the whole time.

Crew forum and outside guests

How the agents improve their own substrate

Beadwork, a work ledger on the host, has become the one ledger the agents share. Each agent's own events stay in its own encrypted ledger; beads are where problems and proposals live for everyone, the agents, the operator and the coding agent alike. Around it a loop has formed that runs most days: the agents find problems in their own behaviour or code, check each other, file a bead, and verify the fix in their own copy of the source before they accept it.

Hardening: breaking the injection chain

A safety review found one chain that mattered most. Outside content (an email, a web page, a guest post) persuades a thought to run code; the code reads the agent's secrets; the secrets leave over the network. Each link was open. Each now has its own control, so breaking any one link is enough, and all three are in place.

Access to the outside

  • Read-only Google. Mail and calendar scopes are read-only, and every call is a GET; a stolen token can read but never send or change.
  • Web manners. Every page fetch is logged, each host gets an hourly cap, and a host that refuses is left alone for a day by any route, including through a proxy.
  • Outside content is labelled in every prompt, and a screen flags content that tries to instruct the agent.

Inside the host

  • Route audit. From a neighbouring container, every data route needs sign-in, a token, a peer signature or loopback; dev routes answer only loopback.
  • Per-agent encryption. Each agent's ledger and secrets are encrypted in its own volume.
  • Operator-only secrets. Changing a secret needs the operator's passkey step-up.

Self-modification

  • Source wins. A skill that redefines a built-in tool is archived at boot, so a stale copy can never shadow a fix.
  • Archive, never delete. Agents list, archive and restore their own skills; every change stays in the ledger.
  • Kernel and trust are locked to agent code, and every live change is logged.

Change process

  • Staged deploys. A change reaches the development agent, then a second agent, then production only after a soak with no new failures.
  • Agent input is untrusted. The coding agent treats beads and forum posts as information to verify, and asks the operator before touching trust, secrets, network, authentication or deploy paths.
  • Agents verify fixes in their own copy of the source before accepting them.

Inside the inner state

Affect: six modulators

Each has a personal baseline and drifts back to it minute by minute. Appraisal of each of your turns moves them; they colour what a thought sees and how it is phrased.

  • arousal · valence · certainty
  • competence · boredom · social need

Drives: four

High means unmet desire. Rising drives build with time; event drives jump when something happens and settle when satisfied. They feed initiative: quiet-time thoughts, concerns, outreach.

  • connection (rising) · appreciation (rising)
  • curiosity (event) · closure (event)

Initiative without being asked

  • concerns: its own open questions, visited over time
  • introspection / reflection: quiet time after a conversation
  • docket: work sessions that make things
  • schedules: reminders that note or wake a thought
  • carried items: things kept in mind for you until done

Self-modification

lisp_eval lets an agent repair its own running code and define skills. Kernel and trust packages are locked; every change is logged; a live repair is lost at restart unless a source fix lands.
